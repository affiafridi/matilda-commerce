## Phase 1 implementation decisions (2026-11-25)

| ID | Decision | Reasoning | Alternatives / revisit |
|---|---|---|---|
| D-014 | **NestJS 11 (CommonJS)**, not 12 | NestJS 12 is ESM-only; ESM plus Jest plus decorator metadata adds friction and risk, and Jest is the approved test runner | Revisit NestJS 12 once ESM tooling is settled; upgrade is a planned task |
| D-015 | **Prisma 7.10.1** with `@prisma/adapter-pg`; client generated into `apps/api/src/generated/prisma` (git-ignored, regenerated by build/typecheck/test) | Prisma 8 is only a release candidate; v7 requires driver adapters and `prisma.config.ts` | Upgrade to 8 when stable |
| D-016 | TypeScript **5.9.3** and ESLint **9.39** (not TS 7 / ESLint 10) | Ecosystem compatibility of Nest, Next, typescript-eslint and ts-jest | Revisit at Phase 2 |
| D-017 | Shared packages compile with `tsc` to CommonJS `dist/`; apps consume built output, so `pnpm build:packages` runs before dev/typecheck/test | Works for both Nest (CJS) and Next without bundler config | Add watch mode or switch to source exports later if DX suffers |
| D-018 | API conventions: global prefix `/api`, URI version `/v1`, health at `/api/v1/health` (liveness) and `/api/v1/health/ready` (readiness, 503 if the DB is down); standard `ApiErrorBody` with `code` and `requestId`; `X-Request-Id` accepted/echoed; Swagger at `/api/docs`, off by default in production | Matches docs/API.md | Surface sub-prefixes (`/storefront`, `/admin`, ...) arrive with their modules |
| D-019 | API tests with Jest + ts-jest + supertest; frontend and package tests with `node:test` for now; Playwright E2E deferred to Phase 5+ | Minimal dependencies; Playwright is not needed until real flows exist | Add Jest/Testing Library for frontends when components appear |
| D-020 | Local PostgreSQL 17 via `docker-compose.yml` with a named persistent volume, published on **host port 5434** (container 5432); Redis only under a compose profile. Dev-only default credentials live in compose/`.env.example` and must never be reused elsewhere | Native PostgreSQL 16 (5432) and 18 (5433) already run on the owner's machine; owner asked for 5433 but it was taken, so 5434 was used without stopping their services | Port is configurable via `POSTGRES_PORT` |

## Phase 2 decisions (approved by owner 2026-11-25: "Approve all")

The owner approved the recommendations of D2-01 to D2-20 in [PHASE-2-PLAN.md](PHASE-2-PLAN.md) section 12 as written: server-side sessions (D2-01); same-origin Next.js proxy with an internal trusted-host secret (D2-02); RLS as a second isolation layer gated by the step 2.2 spike (D2-03); UUIDv7 keys (D2-04); backend dependencies introduced at the step that needs them (D2-05); global staff, per-brand customers (D2-06); global custom roles scoped at assignment (D2-07); role default permission sets drafted by Claude and signed off by the owner before production seeding (D2-08); shadcn/ui + TanStack + React Hook Form with React context for switchers (D2-09); mandatory TOTP for all staff (D2-10); MailPort with dev adapter, invite links shared manually (D2-11); real branch list to be supplied (D2-12); validated admin-context headers (D2-13); guest scope limited to the actor type (D2-14); customer auth API only (D2-15); proposed session/lockout/password values (D2-16); English-only admin (D2-17); audit retained indefinitely (D2-18); separate `matilda_test` database (D2-19); Playwright at step 2.10 (D2-20).

Approval applies to the plan, not to the owner-review gates: step 2.2 (DDL), 2.6 (staff auth) and 2.9 (admin design brief) still stop for review. D2-08 sign-off and the business information in plan section 14 remain outstanding.

**D2-21 (2026-11-25) Admin design direction, approved by the owner at gate 2.9.** The admin ("Matilda Commerce") has its own neutral, minimal enterprise identity, separate from any brand: white and light-grey surfaces, near-black primary buttons and text, colour only for status, Inter, subtle borders, 4px control and 6px panel radii, collapsible sidebar, content using the full width, tables/forms/filters first, no decorative cards, gradients, shadows or animation. Official logo where appropriate (file pending; text wordmark meanwhile); brand colours are not used in the admin; storefronts keep their own identities. Token layer is variable-based and ready for dark mode (not enabled) and uses logical CSS properties for RTL readiness. Light theme and English only in Phase 2 (D2-17 unchanged). Usability references: Shopify Admin, Linear, Stripe Dashboard (no copying). Architecture, security and permissions unchanged. Implementation choices made under it: self-hosted Inter via `@fontsource-variable/inter`, native `<dialog>` for modals, hand-restyled primitives instead of a component-library default look, session CSRF token in memory with a re-issue endpoint.

**D2-22 (2026-11-25) Step 2.10 implementation choices (for owner review).** (a) The scope switcher is a convenience: the selected brand is sent as `X-Admin-Brand` and the API validates it against the person's grants (403 otherwise); markets and branches only narrow what the screens request. (b) Management tables are plain accessible tables with server paging or keyset loading; TanStack Table is not added until a screen needs client-side sorting or column control. (c) Country on markets and branches is a two-letter text field until a countries reference endpoint exists. (d) Playwright runs on the system Microsoft Edge by default to avoid a browser download, on the TEST database only, with its own API (4100) and admin (3101) instances and its own Next build folder. (e) System roles are read-only in the UI as in the API; the only way to adjust one is to clone it.

Implementation notes: D2-04 UUIDv7 is generated by Prisma (`uuid(7)`) and a tiny in-repo helper for raw SQL instead of a `uuid` package (fewer dependencies, same result).
