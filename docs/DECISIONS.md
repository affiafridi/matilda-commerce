# Decisions

Architectural decisions are not changed without discussing with the owner. New entries are appended; superseded entries are marked, not deleted.

## Approved decisions

| ID | Decision | Reasoning | Alternatives rejected |
|---|---|---|---|
| D-001 | Fully custom platform; no WooCommerce/Shopify/Medusa as backend | Owner requirement; need multi-brand/market/branch control and Cake complexity | Medusa, Shopify, WooCommerce multisite |
| D-002 | Domains: Flowers = `matildaflower.com`; Cake = `matildacake.com`; Cookies = `cookiesbymatilda.com` | Owner corrected the master prompt's `matildaflowers.com` and `cookiesbymatildacake.com` (2026-11-25). `matildaflowers.com` is an unrelated site | — |
| D-003 | Modular monolith in pnpm monorepo, one repo | Simplicity, shared code, future separability | Microservices; multi-repo |
| D-004 | Only the API accesses PostgreSQL | Central enforcement of authorization and tenant isolation | Direct DB from Next.js |
| D-005 | Hierarchy Brand → Market → Branch; brand resolved server-side from trusted domain config | Prevent client-trusted tenancy | Client-supplied store ID |
| D-006 | One shared storefront codebase with per-brand themes; one admin; one API | Reuse core once; independent look per brand | Separate codebases per brand |
| D-007 | Authoritative pricing/inventory/payment/order logic only in backend | Security and consistency | Shared frontend business logic |
| D-008 | Per-brand and per-market payment configurations (independent CCAvenue accounts) | Separate settlement accounts | Single shared merchant |
| D-009 | Separate staff and customer authentication; customers brand-specific by default | Security, brand independence | Unified identity |
| D-010 | Permission-based RBAC with scoped assignments; 12 role templates | Flexibility; no role-name checks | Fixed roles |
| D-011 | Money without floating point; historical order snapshots; UTC storage | Accuracy | Float arithmetic |
| D-013 | Official brand name is **"Matilda Flower"** (singular), not "Matilda Flowers". Used in all docs, UI copy, templates and legal text | Owner correction 2026-11-25; matches live site | "Matilda Flowers" |
| D-012 | Phase 0 is documentation only; no phase advance without approval | Owner control | — |

## Phase 1 implementation decisions (2026-11-25)

| ID | Decision | Reasoning | Alternatives / revisit |
|---|---|---|---|
| D-014 | **NestJS 11 (CommonJS)**, not 12 | NestJS 12 is ESM-only; ESM plus Jest plus decorator metadata adds friction and risk, and Jest is the approved test runner | Revisit NestJS 12 once ESM tooling is settled; upgrade is a planned task |
| D-015 | **Prisma 7.10.1** with `@prisma/adapter-pg`; client generated into `apps/api/src/generated/prisma` (git-ignored, regenerated by build/typecheck/test) | Prisma 8 is only a release candidate; v7 requires driver adapters and `prisma.config.ts` | Upgrade to 8 when stable |
| D-016 | TypeScript **5.9.3** and ESLint **9.39** (not TS 7 / ESLint 10) | Ecosystem compatibility of Nest, Next, typescript-eslint and ts-jest | Revisit at Phase 2 |
| D-017 | Shared packages compile with `tsc` to CommonJS `dist/`; apps consume built output, so `pnpm build:packages` runs before dev/typecheck/test | Works for both Nest (CJS) and Next without bundler config | Add watch mode or switch to source exports later if DX suffers |
| D-018 | API conventions: global prefix `/api`, URI version `/v1`, health at `/api/v1/health` (liveness) and `/api/v1/health/ready` (readiness, 503 if the DB is down); standard `ApiErrorBody` with `code` and `requestId`; `X-Request-Id` accepted/echoed; Swagger at `/api/docs`, off by default in production | Matches docs/API.md | Surface sub-prefixes (`/storefront`, `/admin`, ...) arrive with their modules |
| D-019 | API tests with Jest + ts-jest + supertest; frontend and package tests with `node:test` for now; Playwright E2E deferred to Phase 5+ | Minimal dependencies; Playwright is not needed until real flows exist | Add Jest/Testing Library for frontends when components appear |
| D-020 | Local PostgreSQL 17 via `docker-compose.yml` with a named persistent volume, published on **host port 5434** (container 5432); Redis only under a compose profile. Dev-only default credentials live in compose/`.env.example` and must never be reused elsewhere | Native PostgreSQL 16 (5432) and 18 (5433) already run on the owner's machine; owner asked for 5433 but it was taken, so 5434 was used without stopping their services | Port is configurable via `POSTGRES_PORT` |

## Open questions (unresolved business requirements)

**Brand and design**
1. Brand assets for Flowers (logo, colors, fonts, photography); visual review of the live site in a browser.
2. Arabic typography choice and Arabic content/translation owner.
3. ~~Official brand name~~ — **Resolved (owner, 2026-11-25): the official name is "Matilda Flower" (singular), domain `matildaflower.com`.** See D-013.

**Business operations**
4. Branch list for the UAE launch (names, locations, hours, which brands each serves); shared vs per-brand stock at shared branches.
5. Delivery coverage beyond Dubai? Same-day cutoffs; slot structure; rider model (in-house/outsourced); proof of delivery type; live tracking.
6. Delivery fee policy (live site says free delivery in Dubai).
7. Can a single cart/order span brands (e.g., cake + flowers)? Default assumption: **no**, one brand per cart; "Cake + flower combinations" would be a product-level bundle within a brand or cross-brand future feature.
8. Cancellation, refund, and edit policies; perishable returns.
9. Peak traffic expectations (Valentine's, Mother's Day, Eid).

**Finance/legal**
10. CCAvenue accounts per brand: status, domain whitelisting, methods, refund API, test credentials.
11. UAE VAT treatment (5% assumed — to confirm), invoice format and numbering; legal entity per brand (live footer indicates Matilda Cakes and Sweets L.L.C.).
12. Privacy/consent requirements (UAE PDPL), cookie consent; data retention periods; marketing consent for birthdays/anniversaries.
13. Gift card and loyalty legal constraints; shared vs per-brand balances.

**Technical**
14. Hosting provider/region, data residency preference, backup RPO/RTO.
15. Email, SMS and WhatsApp Business API providers.
16. Mapping provider (Google Maps vs alternative).
17. Customer identity: shared across brands in future?
18. Pagination style; staff SSO; separate apps for rider/production vs routes in admin.
19. Product import format and WooCommerce data migration approach.

**Existing sites**
20. Full audit of Cake and Cookies WooCommerce setups (plugins, custom code, workflows) — see [FEATURE-PARITY](FEATURE-PARITY.md).
21. SEO inventory (URLs, rankings, backlinks) and the 301 map — see [SEO](SEO.md).

- A-002: Languages at launch: English and Arabic.
- A-003: One brand per cart/order.
- A-004: Customers and carts are brand-specific.
- A-005: Observations of live sites in this document come from text-only fetches (colors, fonts, imagery not visible) and are unverified.
